# Lane R4 — ragged tangent layer

Scope: `t3toolbox/{frame_variations_format,manifold,corewise,safety}.py`,
`t3toolbox/backend/{fv_conversions,fv_operations,tv_operations}.py`; doc pages `docs/frame_variations.md`,

Run with `PYTHONPATH=/home/nick/repos/T3Toolbox <env python> <script>` from the repros dir.

## Summary

Two code defects, both confirmed by script: (1) `check_fv_pair` never compares the number of cores, so a
`(frame d=3, variations d=2)` pair passes, a `T3Tangent` constructs, and `to_dense`/`corewise_norm`/
`MANIFOLD.project`/`MANIFOLD.norm` return silent partial results while `to_t3`/`apply`/`retract` die with
opaque numpy errors; (2) `tv_project_t3_onto_tangent_space` crashes at `d=1` (empty zipper chain), taking
`MANIFOLD.project_ambient(frame, T3)`, `project_ambient(..., method='t3svd')` and `MANIFOLD.transport` with it,
while every other tangent op — including the dense-contraction projection — works at `d=1`.

Everything else numerically checked is correct to machine precision at asymmetric shapes with `C`/`K` stacks:
the K-over-C broadcast in every `tv_*` op (405 per-element comparisons, error exactly 0.0), the four
`tv_{stack,unstack}_{tangent,frame}_stack` converters and the `T3Tangent.{stack,unstack}_{tangents,frame}`
round trips, `tv_oblique_gauge_projection` (vector-preserving, gauged, idempotent, annihilates vertical
directions), `t3_orthogonal_representations` (all `2d` single-core terms reconstruct `x`; paper-order
right-then-left sweep gives an equivalent representation), the untested `fv_variations_*` /
`fv_variation_shapes` / `fv_frame_reverse`, `MANIFOLD.{inner,norm,project,project_oblique,project_ambient,
transport,retract}` vs dense ground truth (lstsq projection onto the dense unit-variation basis; HS inner;
first-order retraction with error ratios 10.0 per decade), the `COREWISE` twin, and `manifold_dim` vs the dense
tangent-space rank (minimal, non-minimal, and `sharing=`). Every `safety.require` site matches
`docs/numerical_contracts.md`: 20 (op, precondition) pairs raise in safe mode, are silent under `unsafe()`
and silent under jit (closed-over numpy operands and traced pytree operands both).

The remaining findings are doc/comment drift, the most consequential being the paper equation numbers (the
code cites (48)–(49)/(50)–(53)/Fig. 20 where the local `t4s.pdf` has (47)–(48)/(49)–(52)/Fig. 22), the
`tt_variations` shape comment (`rRi` should be `rR(i+1)`), the three `manifold.py` docstrings still claiming
object-identity same-frame, the `eq=False`/aux_data comment plus the batching doc's claim that `T3Tangent` is
`eq=False`, and `set_default_safety`'s "script-level default" (it is per-context: threads see the module default).

## Findings

### R4-1 (C, confirmed) — `check_fv_pair` accepts a d-mismatched (frame, variations) pair
`t3toolbox/frame_variations_format.py:1119-1136`. The hole-shape loops are `zip(xVV, yVV)` / `zip(xHH, yHH)`
with no `len` comparison; `T3Tangent.validate` relies on it. Script `r4_01_check_fv_pair_dmismatch.py`:
```
frame.d = 3 / variations.d = 2
check_fv_pair(frame d=3, variations d=2) -> None
T3Tangent constructed: T3Tangent(shape=(5, 6, 7), ...)
  to_dense().shape      -> (5, 6, 7)          # silent: sum of only the first 2 modes' 4 terms
  corewise_norm()       -> 6.9897...          # silent
  MANIFOLD.project(t).variations.d -> 2 ; MANIFOLD.norm -> 5.362...   # silent
  to_t3()               -> ValueError: all the input array dimensions except ... must match exactly
  apply(ww)             -> IndexError: tuple index out of range
  MANIFOLD.retract(t)   -> ValueError: operands could not be broadcast together with shapes (3,4,1) (2,2,3)
check_fv_pair(frame d=3, variations d=4) -> None ; to_dense -> IndexError
```
House rule: structural problems always error. Fix: `if variations.d != frame.d: raise ValueError(...)` before the
loops (mirror `fv_weights_consistent`, which does compare lengths). The input is malformed (user error), so
this is filed as C rather than S, but note that four public ops return values rather than raising.

### R4-2 (C, confirmed) — `d=1` crashes `tv_project_t3_onto_tangent_space` → `project_ambient(T3)`, `t3svd` method, `transport`
`t3toolbox/backend/tv_operations.py:402-403`: `tt_zipper_left_to_right(other_tt_cores2[:-1], left_tt_cores[:-1])`
gets empty tuples when `d == 1`, and `tt_zipper_left_to_right` does `coresA[0].shape` → `IndexError: tuple index

a hand-listed set starting at d=2. Fix: in `tv_project_t3_onto_tangent_space` handle `d == 1` (the two zippers
are just the boundary `ones` matrices of the stack shape), or make `tt_zipper_left_to_right` return the boundary
matrix for an empty chain; add d=1 to those test structure lists.

### R4-7 (D, confirmed) — `safety.set_default_safety` is per-context, not a "script-level default"
`safety.py:107-110`. `ContextVar.set` affects only the calling context: a worker thread sees the module
default; a call made inside a `safe()`/`unsafe()` block is discarded at block exit; and the function cannot make
*unsafe* the default (it only accepts tolerances). No test references it. Script `r4_05`:
```
main thread after set_default_safety: SafetyTolerances(rtol_numpy=1e-12, rtol_jax=0.001)
worker thread sees:                SafetyTolerances(rtol_numpy=1e-09, rtol_jax=1e-05)   (== module default: True )
after set_default_safety inside safe() block exits: ... 1e-12 ... (the 1e-7 was discarded)
```
Fix: document "current context (thread/task); call at top level before spawning workers", or set the module
`_DEFAULT` as well (and add an `unsafe_default` switch) if a true process-wide default is intended.
