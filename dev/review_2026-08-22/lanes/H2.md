# Lane H2 — ignored/shadowed parameters and twin drift

Scope: every module under `t3toolbox/` and `t3toolbox/backend/` (48 files). Bug class: a parameter
accepted but never read / read after being overwritten / dropped by a forwarding wrapper; defaults that
differ frontend↔backend or ragged↔uniform; the same contract implemented twice and drifted.
All scripts: `scratchpad/repros/H2/` (each has a matching `.out`). Repo untouched.

## Method

1. **AST scan** (`ast_scan.py` → `ast_scan.out`): per function, parameters never loaded in the body;
   parameters whose first event is a store (shadowed); `**kwargs`/`*args` accepted but never read;
   single-delegate wrappers that do not forward an accepted parameter. Assignment targets are visited
   after values (so `x = f(x)` is a read), abstract bodies (docstring + `raise`) are skipped.
   80 raw hits → 46 after the fix; every one hand-checked. Real: `__mul__(use_jax)` (known),
   `block_sumsq_over_*(n_w)` (documented "unused" in its own shape comment — fine), the six
   `Uniform*Kind.forward/transpose` ignoring `ww`/`index`/`s` and `frame_data` (H2-9), `Problem.local_model/objective(data)`
   overwritten when `sample is None` (H2-1). False positives: `CorewiseGeometry.inner/norm`, `UT3Tangent.to_dense`,
   `_zero_jet` (the param sits inside the callee expression), `_tucker_chunk_*(extra)` (documented common signature),
   `IdentityRegularizer.gradient(aux)` (protocol slot). No `**kwargs` is dropped anywhere.
2. **Default diff** (`default_diff.py` → `default_diff.out`): (a) every frontend method vs the backend function
   it calls, for same-named keyword params — **zero** default differences; (b) ragged/uniform twin pairs by name
   (`t3_`/`ut3_`, `fv_`/`ufv_`, `tv_`/`utv_`, `X`/`UniformX`, `T3*`/`UT3*`) — 6 default differences (all
   `sum_over_probes`, H2-4) plus one-sided optional params (`t3svd` rtol/atol — documented; `sum_stack(axis)` H2-7;
   `use_orthogonalization` on weighted norm/inner H2-6; `chunk_size` on `ut3_probe_corewise_derivatives_transpose` —
   known HANDOFF item; `project_ambient(method)` — uniform has no dense form by design).
3. **Behavioural twin sweep** (`twin_behaviour.py`, `repro_tangent_transpose_twins.py`, `repro_assume_orthogonal.py`,
   `repro_rank_sweep_orth2.py`): `to_uniform → op(opts) → to_ragged` vs `op_ragged(opts)` on asymmetric
   shapes `(5,6,7)`, non-minimal ranks (a sum of two T3s), for `t3svd` with scalar/list caps, `assume_orthogonal`
   (truncating, on a non-orthogonal input — honoured on both sides), both `rank_adjustment_sweep` directions,
   `inner`/`norm(use_orthogonalization=False)`, weighted norm/inner, the five tangent transposes ×
   `sum_over_probes` × `chunk_size ∈ {None, 2, 100}` on the **same** frame (`UT3Frame.from_t3frame`), the corewise
   transpose, `to_t3(include_shift)`, `sum_stack`. All agree to 1e-15 except the documented lossy uniform
   right-to-left sweep on a non-left-orthogonal input. (A first pass with independently built frames showed 5e-2
   gaps — gauge, not a bug; the bare `𝒥ᵀ` is frame-dependent, as documented.)
4. **Duplicated normalizers**: ω — `fitting._canonical_weight` vs `backend/fitting._weight_matrix`
   (`repro_omega_backend_lenient.py`, H2-5); sharing — `None` / tuple / list / `np.array` / str labels, all-singleton
   and nontrivial, through `compute_minimal_ranks`, `manifold_dim`, `t3svd`, `rank_adjustment_sweep`, `ut3svd`,
   `ut3_rank_adjustment_sweep`, `continuation_ranks`, `frame_has_minimal_ranks`, `canonical_groups`, `SharedGeometry`,
   `with_sharing`, and a 3-step Newton fit `MANIFOLD` vs `shared_manifold((0,1,2))` (`sharing_normalizers.py`) —
   all agree numerically; only the frontend `SharedGeometry` identity differs (H2-8).
5. Validation-argument gating in `newton_cg`/`make_newton_display` (`repro_val_sample_alone.py`, H2-3).

## Findings

### H2-1 — S (confirmed). `Problem.objective` / `Problem.local_model` silently discard `data=` when `sample` is omitted
`t3toolbox/backend/optimizers.py:178-181` and `:191-197`: `if sample is None: sample, data = self.sample, self.data`.
Passing `data=other` (the documented keyword, same sample) returns the objective on the **training** data.
`repro_problem_data_ignored.out`: `objective(x, data=other)` expected 110081.93, actual 107677.25 (= training value);
`local_model(x, data=other).objective` same. The mirror misuse (`sample=` without `data=`) dies with
`TypeError: unsupported operand type(s) for -: 'float' and 'NoneType'`.
Supported path: `Problem` is the documented backend entry (`least_squares_problem`, user guide §"Frontend and backend");
scoring the training sample against different data (validation targets, a perturbed rhs) is a natural call.
Fix: `if sample is None and data is None: …; elif (sample is None) != (data is None): raise ValueError('pass both sample and data, or neither')`.

### H2-2 — S via documented chain (+ D at 5 sites) (confirmed; found incidentally by the twin sweep). `rank_adjustment_sweep('right_to_left')` is documented to return a **right-orthogonal** T3; on a generic input it does not
`t3toolbox/backend/t3_svd.py:301` ("produces a **right-orthogonal** result"), `tucker_tensor_train.py:4452` and `:791`
(`is_right_orthogonal`: "The result of rank_adjustment_sweep('right_to_left') is right-orthogonal. Use this to verify before
asserting t3svd(..., assume_orthogonal=True)"), `uniform_tucker_tensor_train.py:724`, `docs/t3svd_minimal_ranks.md:74`.
`repro_rank_sweep_chain.out`: on `randn((5,6,7),(3,4,3),(1,3,3,1))`, after the sweep TT cores 1,2 are right-orthogonal
(6e-16) but every Tucker core has `‖BBᵀ−I‖ ∈ {5.3, 12, 23}` — `is_right_orthogonal()` is False (residual ≈ 16); the
`t3_down_svd_tt_core` step pushes the non-orthogonal factor **up** into the Tucker core. The form is reached only when
the input is already left-orthogonal (then True). Consequence of following the docs:
`x.rank_adjustment_sweep('right_to_left').t3svd(max_tt_ranks=2, assume_orthogonal=True)` truncates with relative error
0.2156 vs 0.1652 for `x.t3svd(max_tt_ranks=2)` at identical ranks — silently. The uniform twin behaves the same on the
orthogonality (and is additionally lossy there, which *is* documented).
Fix: either orthogonalize the Tucker cores in the sweep (down-SVD the Tucker core after the bond step so the output is
genuinely right-orthogonal) or reword all five sites to "TT cores right-orthogonal; full right-orthogonal form only for a
left-orthogonal input" and drop the `assume_orthogonal` chain advice from `is_right_orthogonal`.

### H2-3 — C (confirmed). `val_sample` without `val_data` is silently ignored; `val_data` without `val_sample` crashes with a bare `TypeError`
`t3toolbox/backend/optimizer_display.py:215-217` gates on `val_data is not None` only; `t3toolbox/optimizers.py:394-397`
mirrors it. `repro_val_sample_alone.out`: `newton_cg(..., verbose=True, val_sample=wv)` → no val column, no record, no
error; `val_data=bv` alone → `TypeError: 'NoneType' object is not subscriptable` from inside `w_axes`. Backend
`make_newton_display(problem, val_sample=wv)` accepted silently. The map's R5 flagged the crash half; the silent half is new.
Fix: `if (val_sample is None) != (val_data is None): raise ValueError(...)` at both sites.

### H2-4 — E (confirmed). `sum_over_probes` defaults to `False` on the six ragged `tv_*_transpose[_derivatives]_from_sweep` and to `True` on their six `utv_*` twins
`backend/apply.py:276`, `entries.py:212`, `probing.py:1162`, `sampling_derivatives.py:2132/2341/2403` vs
`backend/utv_sampling.py:194/206/218/321/334/350`. Each `utv_*` docstring says it "shares" the `tv_*` function.
`repro_sum_over_probes_default.out`: with defaults the ragged result keeps `W` (`dU[0].shape=(4,2,5)`), the uniform one
sums it (`(3,3,7)`). The frontends (`T3Tangent.*_transpose`, `UT3Tangent.*_transpose`) both default `False`; the sampling
kinds pass `True` explicitly, so no shipped path is affected — but a raw-`.data` user porting ragged code to uniform gets a
different shape. Fix: default `False` on the `utv_*` twins (or state the difference in the docstrings).

### H2-5 — E/C (confirmed). Backend ω normalizer does not validate the mode dimension: an over-long per-mode weight is silently truncated, a short one dies with an `IndexError`
`backend/fitting.py:199-235` (`_weight_matrix`, validates only the order dim; docstring says "the mode dim m in {1, d} is
validated in the frontend") and `:237-290` (`_make_weight`: `wp[i if m > 1 else 0]`). `repro_omega_backend_lenient.out`:
`ProbeKind(weight=[1,2,3,4,5])` on d=3 runs, objective equals `weight[:3]`'s; `weight=[1,2]` → `IndexError: index 2 is out of
bounds`. The frontend (`fitting._canonical_weight`) raises a clear `ValueError` for both. Razor: a backend user gets no
error. Fix: check `m in (1, len(x))` inside the ragged-list branch of `apply_w` (d is known there) with the frontend's message.

### H2-6 — E (confirmed). Ragged frontend `t3_weighted_norm` / `t3_weighted_inner` lack the `use_orthogonalization` kwarg their backend and uniform twins expose
`tucker_tensor_train.py:4800` and `:4806` hard-wire the backend default; `backend/t3_linalg.py:610-632` and the uniform
frontend `uniform_tucker_tensor_train.py:1215/1224` (+ `backend/ut3_linalg.py:183/209`) take it. `twin_behaviour.out`:
`t3_weighted_norm(x, W, use_orthogonalization=False)` → `TypeError: unexpected keyword argument`. Fix: add and forward.

### H2-7 — E (confirmed). `UniformTuckerTensorTrain.sum_stack()` has no `axis` (ragged: `sum_stack(axis=None)`)
`uniform_tucker_tensor_train.py:269` vs `tucker_tensor_train.py:2522`. `twin_behaviour.out`: `uxs.sum_stack(axis=0)` →
`TypeError`. Parity gap, not in the HANDOFF parity list. Fix: add `axis` (the backend `ut3_sum_stack` sums all axes; a
partial sum needs a small extension) or document the restriction in `docs/uniform_equivalence_contract.md`.

### H2-8 — E (confirmed). Frontend `SharedGeometry` identity keys on the raw labels; the backend geometry keys on the canonical partition
`shared_geometry.py:146-158` (`__eq__`/`__hash__` over `self.sharing`) vs `backend/geometry.py` `with_sharing` →
`canonical_groups`. `sharing_normalizers.out`: `shared_manifold(('a','a','b')) == shared_manifold((0,0,1))` is False (hashes
differ) while the backend pair compares equal; `shared_manifold((0,1,2)).precompute(frame)` returns a `SharedFrameData`
where the backend canonicalizes to `()`/`None`. Numerically harmless (a 3-step fit with `MANIFOLD` and
`shared_manifold((0,1,2))` agrees to 0.0), but `GaussNewtonModel` carries the geometry as jit aux, so a relabelled partition
is a second cache entry. Relates to the ledger's "consolidating the sharing-partition normalization" entry (that entry
covers the seven SVD-layer sites, which I verified agree; this is the one site outside it). Fix: hash/eq on
`_groups_from_labels(self.sharing, len(self.sharing))` (no shape needed).

### H2-9 — E (confirmed by AST; impact suspected). The six `Uniform*Kind.forward`/`transpose` ignore their sample (`ww`/`index`/`s`) and `frame_data` arguments
`backend/uniform_fitting.py:94-97, 114-117, 141-146, 162-168, 184-190, 213-219`: the uniform sweep carries the packed
sample and masked frame, so the method args are dead; the ragged kinds (`backend/fitting.py:480-639`) read both. The
shipped `LocalModel` always passes the sweep's own sample, so nothing is wrong today, but a custom caller (or a future
minibatch-by-resampling scheme) that passes a different `sample` to `transpose` than to `precompute` gets the sweep's
sample silently on uniform and the new one on ragged. Fix: a one-line comment on the uniform base noting the args are
carried by the sweep, or an `assert sample is sweep_sample`-style guard in debug mode.

sweep over ~30 optional-argument paths (numpy only, unstacked + one `(2,3)` stack for `sum_stack`); sharing normalizers
at 12 sites × 5 spellings; ω frontend vs backend; `Problem`/display argument gating.
