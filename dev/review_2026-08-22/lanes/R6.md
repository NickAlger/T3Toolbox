## Verdict on the math (the "unvetted derivation" caveat)

**The jet math is correct at asymmetric shapes.** Everything below was run at `d ∈ {1,2,3,4}`, orders
`0..4`, with distinct mode dims, distinct Tucker ranks, `nD != nU` (frame down-core mode dim ≠ up-core
rank), `rL != rR` (left/right TT ranks differ, non-palindromic), and stacks `W ∈ {(),(3,),(2,2)}`,
`K ∈ {(),(2,)}`, `C ∈ {(),(2,)}` — i.e. deliberately outside the suite's `((4,5,6),(2,3,2),(1,2,2,1))`
structure (palindromic ranks, `nD == nU`). `asym_numpy.py` → `TOTAL FAILS: 0` (rel. err ≤ 1e-9 on
every element, most ~1e-15):

- A. plain `t3_{probe,apply,entries}_derivatives` vs `dense_*_derivatives` on `to_dense` of an
  asymmetric T3, every (W, C) element; plus an **independent polynomial oracle** (`poly_jets`: the
  plain op along `s ↦ X + sP` is a polynomial of degree ≤ d, solved exactly by a Vandermonde system,
  `y^(t) = t!·c_t`). This confirms the unnormalised-derivative convention
  (`y^(t) = dᵗ/dsᵗ`, not Taylor coefficients) independently of `dense_*` — order 1 cannot distinguish
  the two, orders ≥ 2 can.
- B. tangent `tv_{probe,apply,entries}_derivatives` vs the dense oracle on the densified tangent
  (`tv_to_dense`, generic non-orthogonal frame with `nD≠nU`, `rL≠rR`) on every (W, K, C) element; same
  polynomial oracle on `tv_probe` / `tv_apply`.
- C. every standard form vs its `_trs` twin (`mu, nu, eta, sigma, tau, deta, tau_tilde, sigma_tilde`,
  both `assemble_*_variation_jets` with `chunk_size=2`, summed and kept), ≤ 1e-11.
- D. adjoint identity `<r, Jv> = <Jᵀr, v>` for probe/apply/entries transposes at the asymmetric shapes,
  `sum_over_probes` True; and kept (`False`) summed over W == True.
- E. corewise transposes vs central finite differences of `<r, forward(cores)>` (1e-5), d = 1..4.
- `chunk_jax.py` §3: **`jax.linear_transpose` of `tv_{probe,apply,entries}_derivatives` (ragged jax,
  x64) equals the hand-written transposes** at d = 1..4, orders 0/2/4, with W+K+C (≤ 1e-10). §4: the
  whole ragged forward + transpose jit-compiles and agrees with eager.
- Symmetric-derivative convention: consistent across `docs/symmetric_probe_derivatives.tex` (Def. 1,
  Eq. oracle), the `dense_*` oracles (`math.factorial(t) * acc`), the docstrings, and
  `docs/entries_apply_probe.md:180`; confirmed numerically by the polynomial oracle.
- `check_perturbation_vectors` / `check_perturbation_index`: match their docstrings (shape-only,
  `np.shape`, jit-safe); frontends call them with `self.shape` / `frame.shape` (both exist).
- In-scope test files pass: `test_jet_recurrence.py`, `test_probe_derivatives.py`,
  `test_chunk_size_estimator.py` → 33 passed, 773 subtests.
- Paper §4 (t4s.txt 798+) is about derivative probes of implicitly-defined maps (lattice of incremental
  solves) — it does not contain the T3 jet recursions; the module and tex note say so correctly. No
  numbered-equation claims in scope to check against the paper.

## Chunking

`chunk_jax.py` §1 (uniform jax arrays, eager **and** `jax.jit`): chunked == dense (≤ 1e-11, shapes
equal) for `n_probe ∈ {1, 2}` × `sum_over_probes ∈ {T, F}` × `chunk_size ∈ {1, 2, 3, W−1, W, W+1, None}`
× orders `{0,1,3}`, for both `assemble_tt_variation_jets` and `assemble_tucker_variation_jets`. The four
early-returns behave as documented: `None` → dense; ragged tuple → dense; `n_probe=2` + kept → dense;
`W <= chunk_size` → dense. `_flatten_w` (n_probe=2, summed) verified exact. **`_wchunked_concat`'s
hard-coded `axis=1` (map R10) is correct today** — the kept path only runs with `n_probe == 1`, where the
per-chunk output is `(d, W, …)`; it would only break if the `n_probe != 1 and not sum_over_probes → dense`
pre-check were removed. Refuted as a bug (fragile, not wrong). Frontend: `T3Tangent.probe_derivatives_transpose`
chunk 2 vs None identical; `UT3Tangent.probe_derivatives_transpose` (jax) adjoint identity holds at
`chunk_size ∈ {None, 2, 100}` (`uniform_adjoint_frontend.py`).

Memory (the claim chunking exists for), via `jit(...).lower().compile().memory_analysis().temp_size_in_bytes`
on `assemble_tt_variation_jets` (d=4, r=24, order 3):

## Findings

### R6-1 (D, confirmed) — the kept (`sum_over_probes=False`) chunk path does not bound memory; docstring says a sequential `lax.map` does
`sampling_derivatives.py:1967-1968` (docstring of `assemble_tt_variation_jets`): "The chunk map is a real
``lax.map`` (sequential), so only one chunk's intermediate is resident." `docs/chunking.md:27-31`: the
partials are "added when W is summed … or concatenated when W is kept … The peak drops from
|W|·(per-row) to chunk_size·(per-row)". Code: the summed path is a `jax.lax.scan` (`:1922-1925`, not
`lax.map`), and the kept path `_wchunked_concat` (`:1931-1939`) is a Python list comprehension +
`concatenate` — unrolled under jit, no scan at all (its own docstring admits "the parts must all be
materialized"). Measured: kept path 359 MB dense → 340 MB at `chunk_size=8` (W=256). Fix: either state in
both places that chunking bounds memory only for `sum_over_probes=True` (the fitting path), or implement
the kept reducer as a scan writing each chunk into a preallocated output with `lax.dynamic_update_slice_in_dim`.

### R6-2 (D, confirmed) — summed path: when `W // chunk_size == 2` chunking is memory-inert (incl. the default `chunk_size=100` for W ∈ [200, 299])
`_wchunked_sum` (`:1907-1928`) computes chunk 0 eagerly and scans over `jnp.arange(1, n_full)`; with
`n_full == 2` that scan has trip count 1, XLA simplifies the loop away, and chunks 0, 1 (and the
remainder) are co-resident. Measured W=200, cs=100: 39.6 MiB vs 42.8 dense (expected ~21.4); W=256,
cs=128: 53.1 vs 57.4; W=300, cs=100 (n_full=3): 21.5 ✓. The docstring `:1958` ("Peak ~ chunk_size *
(per-W-row) instead of W * (per-W-row)") and `docs/chunking.md:29-30` do not hold in that regime; a
user who picks `chunk_size = W/2` ("halve the memory") gets nothing, silently. Fix: seed the accumulator
with zeros of the chunk output shape (`jax.eval_shape(chunk_fn, chunk0, extra)`) and scan over
`jnp.arange(0, n_full)` so the loop has trip count `n_full ≥ 2` whenever chunking engages (alternatively
fold the remainder into the loop via a padded last chunk). Numbers are unaffected (exact either way).

### R6-3 (D, confirmed) — `docs/chunking.md:61-62`: "with NumPy … falls back to the dense assembly regardless of chunk_size" — not what the code does
On uniform **NumPy** arrays the chunk loop does engage (`is_ndarray` gates it, not jax-ness): W=7,
`chunk_size=2` → 4 dense-assembly calls (`followup.py` (b)). Results are identical, so harmless; the
module docstrings (`:1725-1726`, `:1966-1967`) list the real fallbacks correctly. Reword the doc page.

### R6-4 (D, confirmed) — stale provenance text: the "project note" now exists
`:49-50` "will be written up afresh in a project note", `:155` and `:1149` "(Project write-up in
preparation.)" — the write-up is `docs/symmetric_probe_derivatives.tex` (cited by the module docstring
`:10` and both frontends). The tex itself (§Extensions, last paragraph) cites
`docs/ambient_derivative_transpose_note.md`; the file is `docs/contributor/ambient_derivative_transpose_note.md`.

### R6-5 (D, confirmed) — `compute_dxi_tilde_jets` docstring contradicts its shape comment
`:1640-1641` "(output at the order-<=1 leg u)"; the return shape comment `:1638` and both einsums
(`->rWKCi`, `->sWKCi`) give the **full** `(order+1,)` order axis. The `≤1` truncation happens in the
assembly (`dxt[:s_size]` / `dxi_tildes[:, :s_size]`, `:1669`, `:1711`). Delete the parenthetical.

### R6-6 (E, confirmed) — three dead conditionals
`:814`, `:1511`, `:2258`: `reverse = tt_operations.tt_reverse if <cond> else tt_operations.tt_reverse` —
both branches identical (leftover from a uniform/ragged reverse split; `tt_reverse` is polymorphic).

### R6-7 (E) — `K` means both "derivative order" and "tangent stack" in the same docstrings
Signature comments `# highest derivative order K` (`:141, :239, :1105, :1135, :2066, :2107, :2144, :2180,
:2538`) and `dense_probe_derivatives`' `(K+1,Ni)` sit beside "tangent stack ``K``" (`:152, :1145, :2193`),
in the same functions. Rename the order symbol in comments (the tex uses `K` for the order, the library
uses `K` for the tangent block; the library convention should win here).

### R6-8 (E) — test gaps the docstrings paper over
`tv_probe_derivatives_transpose` (`:2197`), `tv_apply_derivatives_transpose` (`:2391`), the module
comments (`:1426`, `:2222`) and the tex say "Verified against … ``jax.linear_transpose``"; `grep
linear_transpose tests/` finds nothing. It does hold (I ran it, d=1..4, orders 0/2/4, W+K+C) — worth a
`test_dispatch` case. Likewise every tangent-derivative test uses one structure with palindromic ranks
and `nD == nU`; the asymmetric builders in `common_r6.py` (generic `T3Frame` with `nD≠nU`, `rL≠rR`,
`tv_to_dense` oracle) would make a cheap extra `subTest` row.
