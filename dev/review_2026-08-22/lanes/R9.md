## Findings (detail)

### R9-1 (S, confirmed) Cross-layer shared companion on `UT3Frame.to_t3frame()` gives a WRONG tied projection
`shared_manifold(spec).project_ambient(frame_u.to_t3frame()[c], z)` returns a tangent 32-33% off the true tied
projection (the uniform shared geometry on `frame_u` and the ragged shared geometry on its OWN frame agree to
1.7e-15), and the result is NOT in the tied tangent space (re-projecting it with the correct companion changes it
by 18-21%). The companion spectrum is right (gauge-invariant), but `fv_shared_frame_data` derives the centers
`H_i` by re-sweeping the left chain with fresh SVDs and pairs them with the stored `O_i`; on the sliced cores of a
`to_t3frame()` leaf the sweep's sign/rotation choices differ from the padded construction, so `S_i^T = <O_i, H_i>`
is inconsistent. The docs cover only the OTHER direction (`t3frame_to_ut3frame`-packed ragged frames,
`docs/uniform_equivalence_contract.md:80-85`, `sharing_internals.md:134-141`); the reverse route is the one
`UniformManifoldGeometry.project_ambient`'s own docstring recommends for dense gradients
(`uniform_manifold.py:1168-1171`: "go via the ragged geometry and the cross-layer converters"), and
`SharedGeometry.shared_frame_data(frame)` is public. Repro: F, section (2). Fix: build the centers gauge-
consistently from STORED cores only -- `H_i = L_i` contracted with the right-chain environment
`tt_zipper_right_to_left(left[i+1:], right[i+1:])` (no SVD, no sign freedom; the frame is consistent by
construction), which also removes the "as stored, not re-masked" fragility; or at minimum document the reverse
caveat and have `fv_shared_frame_data` verify the re-swept right chain matches the stored one.

### R9-2 (C, confirmed) `UniformManifoldGeometry.project_ambient` / `transport` crash on a K-stacked tangent
`UNIFORM_MANIFOLD.transport(v, new_frame)` with `v.tangent_stack_shape=(3,)` (and `project_ambient(frame, grad)`
with grad stack `K+C`, and the `shared(UNIFORM_MANIFOLD, ..)` wrappers) raise
`ValueError: cannot reshape array of size 40 into shape (4,3,2,5,1)` from `ufv_apply_variations_masks`:
`utv_project_ut3_onto_tangent_space` attaches the frame's gauge masks (stack `C`) to variations of stack `K+C`
(`utv_operations.py:574`). The ragged `MANIFOLD.transport` / `project_ambient` accept a `K` stack. Repro: D
(transport block) and F (1). Fix: broadcast the gauge masks over the extra leading stack (the
`utv_sampling._gauge_masks_over_Knew` helper does exactly this), or raise a clear structural error.

### R9-3 (S, confirmed; narrow) Negative `axis` in uniform stack sums hits the MODE axis
`ufv_variations_sum_stack` (`ufv_operations.py:195`) and `utv_sum_tangent_stack` (`utv_operations.py:169`) map
`axis` to array axis `1 + axis`; for `axis=-1` that is axis 0 = the mode index `d`. With `K == d` (e.g. d=3 modes,
K=(3,)), `UT3Variations.sum_stack(axis=-1)` returns a shape-valid object whose content is the sum over MODES with
`K` relabeled as `d` (E2: got shape `(3,2,3,6)` = `(K->d, C, nD, N)` vs correct `(3,3,3,6)`; masks = OR over
modes); otherwise an obscure `Inconsistent shapes for UT3Variations` / `check_ufv_pair` error (E). The ragged
`T3Variations.sum_stack(axis=-1)` follows numpy semantics. Fix: `axis = axis % n_stack` (+ range check) in both
backend functions.

### R9-4 (C, confirmed) `uniform_least_squares_problem(geometry=...)` silently routes any non-'manifold' string to corewise
`uniform_fitting.py:437`: `... if geometry == 'manifold' else UniformCorewiseGeometryOps...` -- `'Manifold'`,
`'MANIFOLD'`, a typo, all build the corewise geometry with no error (B2). Fix: validate against
`('manifold', 'corewise')`.

### R9-5 (C, confirmed) `order=None` for a derivative kind builds a Problem that fails on first use
`uniform_least_squares_problem('manifold', 'apply_derivatives', x0, (ww, pp), data)` (docstring: order
"required") returns a Problem with `kind.order = None`; `prob.objective(x)` then raises
`TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'` deep in the jet code (B2). Fix: raise a
ValueError up front in `uniform_derivatives_kind` / the factory.

### R9-6 (D, confirmed) Module docstring names `save` as a deliberate asymmetry; the real `UT3Variations` gaps are undocumented

are deliberate design" -- but `UT3Frame.save/load` and `UT3Variations.save/load` exist and round-trip (C). The
actual `UT3Variations` asymmetries vs `T3Variations` -- no `to_vector`/`from_vector`/`size`/`data_size`/
`variation_shapes` -- appear nowhere (`naming_conventions.md:205-220` lists only `UT3Tangent`'s). Fix: correct the
example and add the `UT3Variations` line to the asymmetries list.

### R9-8 (D, suspected) "Masking first breaks the pairing" not reproduced
`ufv_shared_frame_data`'s docstring and `sharing_internals.md:134-141` say re-masking the frame before the
companion sweep "changes the sweep's SVD sign choices and BREAKS the pairing (measured)". On the (5,6,5,6)
('a','b','a','b') structure, a zero-padded `frame.apply_masks()` frame gave an identical companion (spectrum and
tied projection, 1.8e-16), while GARBAGE in the frame padding corrupts it (spectrum 3e17, projection 2.5 off)
precisely because it is not re-masked (A2 (e)). One structure cannot refute a data-dependent sign flip, so this
is an observation: the as-stored choice buys nothing here and costs frame-garbage robustness; R9-1's fix would
make the question moot.

### R9-9 (E, confirmed) Wrong-layer frame gives an obscure error
`MANIFOLD.project_ambient(UT3Frame, UniformTuckerTensorTrain)` and `shared_manifold(spec).project_ambient(UT3Frame, ..)`
raise `ValueError: too many values to unpack (expected 4)` (F (3)). A type check would help.

### R9-10 (E, confirmed backlog) `chunk_size` missing from BOTH frontends' `probe_corewise_derivatives_transpose`
The backlog says the uniform `ut3_probe_corewise_derivatives_transpose` hard-codes 100; the ragged frontend
`TuckerTensorTrain.probe_corewise_derivatives_transpose` has no `chunk_size` either (only the ragged backend
does). Numerics are identical across chunk sizes (0.0 / 2.8e-14 uniform vs ragged), so it is a memory/perf knob
only -- no wrong result.

### R9-11 (E, confirmed backlog) `utv_project_ut3_onto_tangent_space` untied at the backend only
The raw backend call leaves a 0.5+ tied residual (expected; no `shared_data=`), but the frontend
`SharedGeometry.project_ambient` / `transport` on the uniform base DO tie (residual < 1e-10, == ragged shared per
element). No silent untie on the frontend.
