# Lane H3 — batching and stacking (hunter lane)

Bug class hunted: stack-axis handling (`C` frame/core stack, `W` probe stack, `K` tangent stack; frame-inner
`W + K + C`; `'...'` vs `contract(...)`; `corewise_dot/norm` collapsing stacks; `C=(1,)` squeeze bugs;
mixed-but-broadcastable stacks; the uniform `(d,)+C+(...)` layout).

Method: four sweep scripts compare every public stacked op **per element** against the same op run on the
sliced (unstacked) element — comparisons on `to_dense()` / norms / scalars, never on cores. Asymmetric
structures throughout: `(5,6,7)/(2,3,4)/(1,2,3,1)` (mode-2 Tucker rank 4 > what the TT can carry, i.e. a
**slack/non-minimal frame**), `(5,6,7,3)/(2,3,4,2)/(1,2,3,2,1)`, `(5,4)/(3,2)/(1,2,1)`, `(6,)/(3,)/(1,1)`.
Stacks: `C ∈ {(), (1,), (3,), (2,3)}`, `K ∈ {(), (2,), (4,)}` over `C ∈ {(), (1,), (3,), (2,3)}`,
`W ∈ {(), (4,), (2,2)}`; `sum_over_probes ∈ {False, True}`; derivative `order = 2`.

## Sweep tallies

- `sweep_t3.py`: **OK 2032 / 20 non-bugs** (see table).
- `sweep_tangent.py`: **OK 3618 / 40 fails**: 8 are H3-2 (`d=1` `project_ambient`/`transport`, every `(C, K)`); the other 32 are a wrong reference in my `COREWISE.retract dense` check (I compared the additive retraction against `x.to_dense() + p.to_dense()`, but `p.to_dense()` is the *linearized* tangent and the additive retraction is multilinear in the cores, so they differ by design — the per-element `COREWISE.retract` vs unstacked-call check passes for every `(C, K)`). All adjoint identities and all per-element transposes/derivative transposes pass in both `sum_over_probes` modes.
- `sweep_uniform.py`: **OK 3624 / 30 fails**, all accounted for by H3-1 (20: every `K ≠ ()` case, d=2,3,4) and H3-7 (10).
- `mixed_and_gn.py`: all GN-model stacked checks match; all mixed-stack combinations rejected.

**Bottom line for the bug class:** no silent wrong answer was found in any stacked op of the ragged layer or
the uniform layer. The frame-inner `W + K + C` convention is implemented consistently across
`TuckerTensorTrain`, `T3Frame`/`T3Variations`/`T3Tangent`, both geometries, the weights, the six transposes,
the derivative ops, the `GaussNewtonModel`, and all uniform twins, for every stack combination tried (incl.
`C=(1,)`, two-axis `C=(2,3)`, two-axis `W=(2,2)`, and `K` over two-axis `C`). The findings below are
crashes on supported stacked paths, one ragged/uniform asymmetry, and doc/comment mismatches.

## Findings

### H3-1 (C, confirmed) — `UNIFORM_MANIFOLD.transport` / `project_ambient` crash for a tangent-stacked (`K ≠ ()`) `UT3Tangent`; ragged twin works

`t3toolbox/backend/utv_operations.py:574` — `utv_project_ut3_onto_tangent_space` builds the gauge masks
from the **frame** (`ufv_variation_masks(frame masks)`, stack `C`) but the ungauged variations `dB`/`dG` it
computes carry the **gradient's** stack (`K + C` when `x_data` is `K`-stacked). It then calls
`utv_orthogonal_gauge_projection(frame_data, (dB, dG, shape, gauge_masks))`, whose
`ufv_apply_variations_masks` (`ufv_masking.py:150-154`) reshapes the `C`-stacked masks to
`(d,)+ss+...` with `ss = K + C` read off the supercore → `ValueError: cannot reshape array of size 9 into
shape (3,2,3,1)`.

Reach: `UNIFORM_MANIFOLD.transport(v, new_frame)` is `project_ambient(new_frame, v.to_ut3())` and
`v.to_ut3()` carries `K + C` — so **transport of any tangent-stacked uniform tangent crashes**. The ragged
`MANIFOLD.transport` handles the same input (sweep: `transport` passes for every `(C, K)`), and the
`UT3Tangent` class docstring advertises the `K` stack ("extra tangent stack `K` over the shared frame stack
`C`"). `UniformManifoldGeometry.transport`'s docstring carries no `K` restriction. The backend signature
comment does say `x_data ... supercore stack = C` (`utv_operations.py:541`), so the backend's own contract
is narrower than the ragged twin (`tv_project_t3_onto_tangent_space` is "Stack-aware" and accepts `K+C`
against a `C` frame — verified). `tests/test_uniform_manifold.py:1177 test_transport` explicitly tests "No
K".

Repro: `repros/H3/repro_uniform_transport_K.py`
```
ragged: tangent_stack_shape (2,) -> transport dense shape (2, 5, 6, 7)
uniform: tangent_stack_shape (2,)
uniform transport RAISES ValueError cannot reshape array of size 9 into shape (3,2,3,1)
ragged project_ambient(frame C=(), grad K+C=(2,)) -> (2,)
uniform project_ambient RAISES ValueError cannot reshape array of size 9 into shape (3,2,3,1)
uniform transport with K=() -> (5, 6, 7)
```
Fix: in `utv_project_ut3_onto_tangent_space`, broadcast the four gauge masks over the leading `K` axes of
`dB`/`dG` before calling the gauge projection (e.g. `np.broadcast_to(m, (d,) + K + m.shape[1:])` with
`K = dB.shape[1:-2][:len(dB.shape[1:-2]) - len(C)]`), or make `ufv_apply_variations_masks` right-align the
mask stack under the supercore stack the way the ragged `'...'` einsums do. Add a `K` config to
`test_transport` / a `project_ambient(K+C grad)` test.

### H3-2 (C, confirmed) — `MANIFOLD.project_ambient(frame, T3 grad)` and `transport` crash for `d = 1` (`IndexError` in `tt_zipper_left_to_right`)

`t3toolbox/backend/tt_operations.py:180` — `ss = coresA[0].shape[:-3]` reads the stack shape off the
first core; `tv_project_t3_onto_tangent_space` (`tv_operations.py:402-403`) calls it with
`other_tt_cores2[:-1]` / `left_tt_cores[:-1]`, which are **empty** for `d = 1`, so `coresA[0]` raises
`IndexError: tuple index out of range`. The dense-gradient path (`tv_project_dense_onto_tangent_space`),
`retract`, `project`, the sampling ops and everything else work at `d = 1` (the ragged `d=1` structure is
used across the suite and `sweep_t3.py` passes it). Stacked `d=1` (`C=(3,)`) fails the same way.

Repro: `repros/H3/repro_d1_project_ambient.py`
```
d=1 project_ambient(frame, dense grad) -> (6,)
d=1 project_ambient(frame, T3 grad) RAISES IndexError tuple index out of range
d=1 transport(v, frame) RAISES IndexError tuple index out of range
d=1 retract OK
d=1 stacked C=(3,) project_ambient RAISES IndexError tuple index out of range
```
Fix: in `tt_zipper_left_to_right` handle an empty core tuple (return `()`? the caller then needs the
boundary environment `Z_0` only), or in `tv_project_t3_onto_tangent_space` short-circuit `d == 1` (the
left/right environments are the `1×1` ones matrices). Uniform `d=1` is already a ledger item (fails earlier,
in `ut3svd_supercores`), so this is ragged-only.

### H3-3 (D, confirmed) — `TuckerTensorTrain.probe` return shape-comment says `X+W+(Ni,)`; the code returns `W+C+(Ni,)` and the prose drops `C`

`t3toolbox/tucker_tensor_train.py:3483` — `) -> Sequence[NDArray]:     # zz, len=d, elm_shape=X+W+(Ni,)`.
`X` is not a block letter anywhere in the library, and the order is frame-*outer*. The sweep asserts the
actual shape is `W + C + (Ni,)` (frame-inner, as `probe_ambient_transpose` at `:3556` and the batching doc
§2 state). The Returns prose (`:3497-3499`) says `elm_shape=W+(Ni,)`, dropping the T3 stack entirely.
(`map_core_ragged.md` flagged this; here it is confirmed against the measured shapes.)
Repro: `sweep_t3.py` (`probe` checks assert `np.shape(zz[k]) == Wsh + C + (shape[k],)` — all pass).
Fix: `# zz, len=d, elm_shape=W+C+(Ni,)` and `elm_shape=W+C+(Ni,)` in the prose.

### H3-4 (D, confirmed) — `entries` / `apply` docstrings call the convention "base-inner"; the library term is "frame-inner", and `idx_stack_shape+t3_stack_shape` / `vec_stack_shape+t3_stack_shape` are the `W+C` letters nobody else uses

`t3toolbox/tucker_tensor_train.py:3294-3296` (entries) and `:3404-3406` (apply). The behaviour is correct
(`W + C`, verified per element). Terminology-only; `docs/batching_and_stacking.md` §9 says "`apply`/`entries`
are `W+C`". Fix: "frame-inner: the index stack `W` is outer, the T3 stack `C` inner", `shape=W+C`.

### H3-5 (E/D, confirmed) — ragged backend `ManifoldGeometryOps.inner` / `CorewiseGeometryOps.inner` / `point_norm_sq` collapse the frame stack `C` to a scalar; the uniform twins (and the frontend `MANIFOLD.inner`) return shape `C`

`t3toolbox/backend/geometry.py:216, 286, 290` use `cw.corewise_dot(a, b)` — the doc-listed gotcha
("collapses EVERY axis, stacks included"). `UniformManifoldGeometryOps.inner` (`:400`) uses
`utv_corewise_inner(..., self.n_stack)` and returns shape `C`; the frontend `MANIFOLD.inner` returns
`K + C`. The `Geometry` protocol (`backend/optimizers.py:90`) says "coordinate `<.,.>` on tangents" with no
stack statement. Today this is latent: every consumer (`gradient_descent`/`mc_sgd`/`adam`/`newton_cg`,
`IdentityRegularizer`) rejects stacked points up front, and `GaussNewtonModel` never calls `geom.inner`
(its stacked per-element results all match, see `mixed_and_gn.py` (b)). But a raw-`.data` user composing
their own loop from the backend geometry (the razor's audience) gets a silently summed-over-`C` inner
product from the ragged geometry and a per-element one from the uniform geometry for the same stacked
input. `CorewiseGeometryOps.point_norm_sq` at least documents "Collapses every axis, stacks included";
`inner` does not.
Repro: `repros/H3/repro_misc_stack.py`
```
ragged  ManifoldGeometryOps.inner on C=(3,) -> shape ()
ragged  ManifoldGeometryOps.point_norm_sq on C=(3,) -> shape ()
uniform UniformManifoldGeometryOps.inner on C=(3,) -> shape (3,)
uniform UniformManifoldGeometryOps.point_norm_sq on C=(3,) -> shape (3,)
frontend MANIFOLD.inner on C=(3,) -> shape (3,)
```
Fix: either use `corewise_stack_dot(a, b, n_stack)` with `n_stack = len(self.stack_shape(...))` (needs the
stack length — the uniform geometry gets it from its fields; the ragged one could read it off the variation
cores' ndim given the known core ndims), or state "stacks collapse" in the protocol and both ragged docstrings.
Related: ledger "Stacked optimization" (deferred) — this is the primitive that would need to be per-element.

### H3-6 (E, confirmed) — obscure errors on rejected stack mixes

- `x(C=(3,)) * dense_of_x(C=())` → bare `AssertionError` with no message (`tucker_tensor_train.py:2023`,
  `assert(other.shape == self.stack_shape + self.shape)`). Every other mixed-stack combination raises a
  clear `NotImplementedError`/`ValueError` ("Cannot add TuckerTensorTrains with different stack shapes",
  "t3m stack_shape mismatch", "Inconsistent (T3Frame, T3Variations) pair", "Tangent vectors have different
  stack shapes ..."). `map_core_ragged.md` lists the `assert`-as-structural-check pattern generally; this is
  the one a stacked user hits.
- `T3Tangent.stack_tangents([v(K=()), v(K=(2,))])` (mixed tangent stacks at one frame) →
  numpy "setting an array element with a sequence ... inhomogeneous shape" from
  `tv_stack_tangent_stack` (`manifold.py:1111`), instead of the structure check `stack_frame` does at
  `:1120-1125`.
- `TuckerTensorTrain.has_numerically_minimal_ranks()` on a stacked T3 raises `t3svd`'s "Cannot use rtol or
  atol with t3svd for stacked Tucker tensor train" (`:758`); the docstring does not say it is unstacked-only
  (`T3Frame.has_numerically_minimal_ranks` is per-element and works stacked). Minor.
Repro: `repros/H3/repro_misc_stack.py` (first five lines of output).

### H3-7 (E, confirmed) — `UniformTuckerTensorTrain * UniformTuckerTensorTrain` raises an obscure numpy error

`t3toolbox/uniform_tucker_tensor_train.py:246` `__mul__` is scalar-only ("Scale by a scalar."); passing a
`UniformTuckerTensorTrain` reaches `xnp` arithmetic and dies with "all the input arrays must have same
number of dimensions ... array at index 1 has 0 dimension(s)". The elementwise-multiply parity gap itself
is already in `map_uniform_weighted_tests_docs.md` §1c; the finding here is only that the unsupported call
is not rejected with a `TypeError`. Repro: `repro_misc_stack.py`.

### H3-8 (E, confirmed) — `COREWISE.retract` on a `MANIFOLD`-frame tangent whose frame has slack (`nU ≠ nD`) fails with a raw broadcast error

`manifold.py:1479-1491` documents "`p` must be a corewise tangent (a frame from `frame`)" but does not check
it; with a slack orthogonal frame (`up_ranks (2,3,4)` vs `down_ranks (2,3,3)`, produced by
`t3_orthogonal_representations` of a non-minimal `x` — the asymmetric structure the brief asks for) the
additive retraction hits `operands could not be broadcast together with shapes (4,7) (3,7)`; with a minimal
frame it silently "works" (adds manifold variations to `(U, P)`), which is the more dangerous half. Not a
stacking bug (identical for every `C`, `K`); recorded because the stacked sweep tripped on it. Repro:
`repro_misc_stack.py` (last two `retract` lines). Fix: assert `p.frame` is a corewise frame (`down is left is
right`, or `nU == nD`) in `CorewiseGeometry.retract` / `CorewiseGeometryOps.retract`.

### H3-9 (D/E, confirmed by reading) — `backend/tv_operations.py` still documents the stacks with the pre-rename letters `V` (tangent stack) and `G` (frame stack)

`tv_operations.py:254-256, 498-503, 542-565` ("each core stack = V + G", "the extra tangent stack V
outermost"). `docs/batching_and_stacking.md` §8 states the block letters are `W/K/C`, "deliberately
disjoint" from the core symbols, and that "`V` here means only the Tucker variation and `G` only the TT
core — no overload". In this module `V`/`G` are simultaneously the Tucker-variation / TT-core symbols and
the stack letters. (`map_core_ragged.md` §2B flags it; included here because it is the one module where the
doc's "no overload" promise is false.) Fix: `V + G` → `K + C` in the comments/docstrings (the
`tv_{stack,unstack}_{tangent,frame}_stack` family and `tv_to_t3`).

## Coverage

Everything listed in the scripts table above, run with the env Python on numpy. Per-element comparisons on
`to_dense`/norms for: all `TuckerTensorTrain` public ops that accept a stacked object (arithmetic, linalg,
SVD/rank ops, orthogonalizations, structural ops, conversions, I/O round-trips, weights, the 3 sampling ops,
6 transposes, 3 derivative ops, 3 derivative transposes); all `T3Frame`/`T3Variations`/`T3Tangent` ops and
both geometries (incl. `project_ambient` with `C` and `K+C` grads, dense and T3, both methods; `transport`);
the two-axis `stack/unstack` pairs and `sum_tangents`/`sum_stack`/`sum_stack_corewise`; `T3Weights` and
`T3FrameWeights` (incl. the `K+C`-weight rejection); every uniform twin of the above; `GaussNewtonModel`
on stacked frames for apply/probe/entries (objective/gradient/jacobian/gn_quadratic/gn_hessian/evaluate,
`K`-stacked trial tangent); the backend `ManifoldGeometryOps`/`UniformManifoldGeometryOps` `inner`/
`point_norm_sq`/`stack_shape`; every mixed-stack combination of two objects (T3×T3, T3×dense, tangent×tangent,
stack_tangents/stack_frame mixes, per-mode mixed `W` in `ww`); the `C=(1,)` stack against unstacked in every
sweep. Callers of `corewise_norm`/`corewise_dot` were enumerated by grep (`backend/geometry.py:216,286,290`,
`backend/optimizers.py:704`; the rest are doctests/`corewise_stack_*` users) and checked (H3-5; `:704` is
behind the stacked-point rejection).

## Not checked

- jax/jit paths of the stacked ops (numpy only — the dispatch convention makes the numbers identical, and
  `test_dispatch` covers invocation); `vmap` over `T3Tangent`.
- Sharing (`shared(...)` geometry, `sharing=` on `t3svd`/`resize`) under stacks — the HANDOFF already notes
  the uniform tied-tangent ops are tested unstacked only.
- Uniform **varying-rank** stacks (the determinantal-variety batches built by `stack`-ing heterogeneous
  trees) — all uniform objects here came from `from_t3` of a single ragged stacked object (uniform ranks
  across `C`).
- The optimizers themselves on stacked points (rejected by design — ledger "Stacked optimization").
- `probe_derivatives_transpose` with `chunk_size` engaged (uniform+jax only).
- `T3Tangent.save/load`, `T3Frame.save/load` round-trips with stacks (they write `.npz`; skipped per the
  brief's CWD warning).
