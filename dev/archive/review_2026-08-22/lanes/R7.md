### Scripts and what they showed

- `reg_objective_raw_x0.py` — the known regularized-`Problem.objective` bug, fully characterized.
  Only a **direct backend `Problem.objective(x)` call at a raw non-left-orthogonal point on the ragged
  MANIFOLD geometry** is wrong (reg term read as `½λ‖last TT core‖²` = 3.13 vs the true 1403.5; total
  1998.03 vs 3398.41). Correct everywhere else: COREWISE (exact for any cores), the uniform twin
  (orthogonalizes first: 3398.41), `LocalModel.objective` at the same raw point (via the frame),
  frontend `GaussNewtonModel.objective_value`, and **every optimizer's recorded number**: `newton_cg`
  `history[0].objective` and `gradient_descent` `losses[0]` come from the LocalModel (frame-based), and
  every later `Problem.objective` call is at a retraction output, which is left-orthogonal to ~1e-15 for
  both the unshared `tv_retract` and the shared grouped-`t3svd` retraction (measured 1.8e-15 / 8.9e-16).
  So the Armijo tests are consistent (`f` and `f_new` both exact) and no stats row is affected.
- `armijo_exhaustion.py` — ran Newton past the precision floor (`gtol_rel=1e-30`). Iterations 12–13 had
  `ls_steps=40`, `alpha=9.095e-13`, `delta_f=+3.3e-28 / +3.2e-27` — the objective **increased** and was
  accepted, 40 objective evaluations each, no failure field. `gradient_descent` from that point: ~25
  objective evals per iteration, losses non-monotone (4.96e-28 → 8.94e-28 → 1.72e-27), nothing in stats.
  Code reading: the loop halves `alpha` *after* the last trial, so on exhaustion the recorded `alpha` is
  `2^-40` while `x_trial`/`f_new` were computed at `2^-39`; `delta_f`, `predicted`, `rho`, `step_rel` on
  that row describe a step not taken.
- `display_val_no_sample.py` — `make_newton_display(problem, val_data=vd)` and the frontend
  `newton_cg(verbose=True, val_data=vd)` both die with `TypeError: 'NoneType' object is not
  subscriptable` at `backend/fitting.py:435` (`_WwSample.w_axes`). `val_sample` alone is silently ignored.
- `weight_contract_drift.py` — the two ω implementations. Frontend rejects a per-mode weight with
  `m ∉ {1,d}`; the backend `probe_kind`/`probe_derivatives_kind` **accept `m > d` and silently use only
  the first `d` rows** (`sumsq` identical with `w[:d]`); `m < d` raises an `IndexError` only at `sumsq`
  time. Aliasing is safe: the frontend's `np.asarray` view is copied by the backend `__post_init__` on
  both layers (`shares_memory=False`, uniform weight non-writeable; mutating the user array after model
  build does not change the objective). 2-D `(d,1)` on plain probe: frontend rejects / backend accepts —
  documented.
- `minibatch_lambda_custom_draw.py` — `_minibatch_step_problem` scales λ by `min(batch,n)/n` from the
  **nominal** `batch`, not the custom draw's size: draw size 5 of n=100 with `batch=50` → factor 0.5 vs
  the draw-consistent 0.05. User-visible: `mc_sgd(..., draw=my_draw, regularizer=...)` with the same draw
  and seed returns different results for `batch=5` vs `batch=50` (rel diff 0.88); unregularized the two
  are bit-identical. So the signature comment "ignored if draw given" (4 sites) and §4.9 "λ keeps the
  same meaning whatever batch size you use" are false for a custom draw with a regularizer.
- `shared_untied_x0.py` — (i) `SharedGeometry.frame(untied x)` in safe mode: no error, ties silently
  (docs claim a safe-mode check). (ii) The backend geometries the optimizers use do **not** tie at
  `frame` (base point of the backend frame at an untied x is untied); the first retraction ties. (iii)
  On an untied base the backend corewise retraction aliases **member 0** (`U[0]+mean(V)` at every group
  mode) while the frontend `SharedGeometry.retract` ties by the **mean** (`mean(U)+mean(V)`) — dense rel
  diff 1.33 between the twins. (iv) On a **tied** base all four `SharedGeometry.retract` branches are
  bit-identical with the backend twins (max abs diff 0.0 ragged; dense rel diff 0.0 uniform).
- `cg_dense_compile_display.py` — `_cg_core` vs a dense pinv solve of the 40×40 GN system (rank 20,
  regularized manifold): `‖p_cg − p_dense‖/‖p_dense‖ = 6.2e-15`, `‖Hp+g‖ = 2.2e-14`. Forcing-term /
  `g0norm_newton` / `g0norm_cg` / `cg_forcing_power` semantics match §5 and the docstring exactly
  (chained fallback verified; `NewtonInfo.g0norm` is the Newton reference). Display `train_err`/`val_err`
  match a hand computation of `‖r_ij‖/‖y_ij‖` per (mode, order) to 4e-16 / 2e-16 (probe_derivatives,
  per-order weight attached). `gradient_descent(use_jit=True)` → `TypeError`. All four optimizers raise
  `NotImplementedError` at entry on a stacked x0. Compile counts: `jit(_cg_core)` cache size **1** after
  a 6-step shared+regularized Newton run, still 1 after a second run with rebuilt geometry/kind/
  regularizer objects; `jit(_mc_sgd_step)` cache size 1 after 30 regularized steps — the compile-once
  claims hold.
- `misc_checks.py` — `mc_sgd` `stats['losses']` are the EMA-smoothed values (`losses[0]==raw[0]`,
  `losses[1:]` differ: 119.67 vs 95.17 ...). The uniform `step_rel` mask-unaware norm: after three
  uniform Newton retractions the supercore padding was exactly zero (masked and unmasked norms equal),
  so no observable effect in practice (map R8 refuted as a practical matter; the code comment stands).

## Findings

### R7-1 (S, confirmed, related to the known item) — regularized `Problem.objective` at a raw point: full characterization
`backend/geometry.py:71–81` / `backend/optimizers.py:191–204`. Affected: direct backend `Problem.objective(x)`
at a raw non-left-orthogonal ragged-MANIFOLD point (shared or not). Not affected: COREWISE, the uniform
twin, `LocalModel.objective`, `GaussNewtonModel.objective_value`, all four optimizers' stats and line
searches (retraction outputs are left-orthogonal to 1e-15, shared included). Cleanest fix: make
`ManifoldGeometryOps.point_norm_sq` exact by left-orthogonalizing first (what the uniform twin already
does) — one sweep per `Problem.objective` call, which is cheap next to the forward it sits beside; or,
if that sweep is unwanted, state the left-orthogonal precondition in the `Geometry` Protocol docstring
for `point_norm_sq` and in `IdentityRegularizer.value`, not only in `Problem.objective`.

### R7-2 (D with S consequence, confirmed) — `batch` is not ignored when `draw` is given + a regularizer
`backend/optimizers.py:237–250` (`_minibatch_step_problem`), signature comments at
`backend/optimizers.py:415, 459` and `t3toolbox/optimizers.py:243, 267` ("ignored if draw given"),
`docs/fitting_and_optimization.md:405–406`. Fix: derive the factor from the drawn minibatch
(`kind.n_measurements(sample_B) / n` — shape-derived, static under jit) inside the step kernel, or
change the four comments and §4.9 to say the *nominal* `batch` governs the λ scaling.

### R7-3 (C, confirmed) — `val_data` without `val_sample` crashes deep inside
`backend/optimizer_display.py:215–217`; frontend `t3toolbox/optimizers.py:394–398`. Fix: raise a
`ValueError("val_sample and val_data must be given together")` when exactly one is given.

### R7-4 (D, confirmed) — three places claim a safe-mode tied check at `SharedGeometry.frame`; it ties silently
`shared_geometry.py:85–87` (class docstring), `:100` (doctest comment), `docs/sharing.md:250–252`,
`t3toolbox/fitting.py:467` comment — vs the method docstring `:169–174` and the code `:175–180`.
Fix: keep the silent tie (the method's own contract) and correct the three claims.

### R7-5 (D/E, confirmed) — "an untied initial guess is a non-event for the optimizers" is not what the backend does
`shared_geometry.py:173–174` vs `backend/geometry.py:166–169` (no tie at `frame`) and
`backend/geometry.py:122–139, 270–273` (corewise retract aliases member 0 vs the frontend's mean at
`shared_geometry.py:285–296`). Fix: tie in the backend `frame` when `groups` is non-empty
(`t3_tie_tucker_factors`, a bitwise no-op on tied input), which makes the twins agree and the docstring
true; or soften the docstring to "for the frontend model path".

### R7-6 (S minor, confirmed, backend-only) — backend probe kinds silently truncate a per-mode weight with `m > d`
`backend/fitting.py:257–261` (`apply_w` indexes `wp[i]` for `i < d`); `:212–213` delegates the mode
check to the frontend. Supported path: raw-`.data` user building `probe_kind(weight)`. Fix: in `apply_w`,
`if m > 1 and m != len(x): raise ValueError(...)` (ragged), same against `x.shape[mode_axis]` (packed).

### R7-7 (E, confirmed) — Armijo exhaustion accepts the last trial silently, and records the wrong `alpha`
`backend/optimizers.py:691–699` (newton), `:402–407` (gradient descent). Demonstrated objective increases
accepted at the precision floor; the recorded `alpha = 2^-40` is one halving past the step taken
(`2^-39`). Fix: on exhaustion reject the step (keep `x`), set an `ls_failed` field on `NewtonInfo`,
and record the alpha actually used (or break before the final halving).

### R7-8 (D, confirmed) — the `Geometry` protocol description under-specifies the backend contract
`docs/fitting_and_optimization.md:228–235` lists `frame/project/retract/inner/norm/precompute`; the
Protocol at `backend/optimizers.py:59–97` has nine members, no `norm`; `point_norm_sq`/`point_tangent`
are required under a regularizer, `base_point`/`stack_shape` always. `release_notes.md:28–33` says
"three more members" and omits the two regularizer ones. Also the §3 structure block (`:196–206`)
omits `backend/apply.py`, `entries.py`, `uniform_fitting.py`, `regularization.py`,
`optimizer_display.py`, and `:99` says all optimizers return a `TuckerTensorTrain` (uniform in → uniform
out). Fix: enumerate the nine, mark which two are regularizer-only, refresh the structure block.

### R7-9 (E, confirmed) — `mc_sgd` `stats['losses']` are EMA-smoothed, undocumented
`backend/optimizers.py:452` (`s_hist`); docs §2.1 `:79` calls them "the full-batch loss checks".
Fix: say "smoothed" in the stats comment/docs, or record both.

### R7-10 (D, confirmed) — `gradient_descent` has no `use_jit`; stale plan reference
`backend/optimizers.py:385` "(Eager; the jit kernel + the `xwhile` line search come in G3.3/G3.4.)";
frontend `t3toolbox/optimizers.py:212–233` never says it is eager-only while the other three advertise
`use_jit`. `TypeError` on `use_jit=True`. Fix: delete the parenthetical; add "eager only" to the frontend.

### R7-11 (E, confirmed by reading) — `_resolve_chunk_size` device pull + duplicated magic 100
`t3toolbox/optimizers.py:135–144`: `np.asarray(x0.tucker_supercore)` etc. only to read `.shape` (a
device→host copy on a jax x0); `return 100` without jax duplicates the kind's default though chunking
never engages without jax. Fix: use `.shape`; return `None` without jax.

### R7-12 (D, confirmed by reading) — `apply_derivatives_model` signature claims ragged-only
`t3toolbox/fitting.py:576–583` (`x: t3.TuckerTensorTrain`, `# MANIFOLD / COREWISE`) vs the body `:617`
dispatching on `UniformTuckerTensorTrain`; the other five factories use the `Union` + "or the UNIFORM_*
twin" spelling. Fix: match the siblings.

### R7-13 (E, suspected) — `SharedGeometry` pytree unflatten drops a subclass
`shared_geometry.py:390–393` reconstructs a plain `SharedGeometry`; a subclass (the case the `__eq__`
comment at `:146–152` guards against) crossing a jit boundary comes back as the base class. Would be
confirmed by jitting `lambda g: g` on a subclass instance and checking `type`. Fix: `type(g)` in the
aux and `aux[2](...)` in unflatten, or convert to a `ValueHashedFields` dataclass (map R2).

### R7-14 (E, confirmed by reading) — `LocalModel.retract` return annotation
`backend/optimizers.py:159` `-> Tangent` for a returned point. Trivial.
